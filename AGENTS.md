# Engineering Skills & Workflow Standards (parquet-tools)

Expectations for contributors to the parquet-tools Go CLI project.

---

## Project Domain Skills

- Parquet format: metadata, schemas, compression.
- Go for CLI tools and streaming IO.
- Parquet storage backends: local, S3, GCS, HTTP.

---

## Go Engineering Standards

- Idiomatic Go; run `gofmt`/`goimports`.
- Handle errors explicitly. Give useful CLI feedback.
- Comment intent, never what the code already says. One line on a declaration, longer reasoning in the body. Past two lines, make the code clearer instead.
- Use `context.Context` for cancellable operations.
- Do not leak goroutines or allocate needlessly.
- Keep non-test files under 300 LOC, never over 500. Split larger ones. Test files may run longer for table coverage and fixtures.

---

## Testing & TDD Expectations

- Pair every source file with a test file: `foo.go` ↔ `foo_test.go`.
- Cover typical and edge cases.
- Use **table-driven tests** for core logic.
- Update golden files under `testdata/golden/` thoughtfully.
- Generate new test data in `testdata/gen/`, Go preferred. Update `scripts/update-golden.sh`.
- Follow **TDD**: write tests first, and watch them fail before implementing.

---

## CLI & Documentation Quality

- Give flags and subcommands clear help text.
- Keep output formats consistent and stable.
- Reflect every behavioral change in `README.md`.
- Keep user examples runnable and tested.
- Keep compatibility notes current.

---

## Contribution Workflow Norms

- **Commit as soon as `make all` passes.** Do not wait to be asked.
- Sign every commit.
- One commit per logical change, tests and docs included. Fold fixups into the commit they belong to.
- Follow **Conventional Commits**.
- **No AI/agent attribution anywhere in the repo.** No `Co-Authored-By`, `Generated by ...`, or similar in commits, PRs, issues, or docs.
- Do not break compatibility without a migration note.
- Push and file PRs against `origin` unless told otherwise.

---

## Quality Gates

- `make all` must pass before merging.
- Hold coverage at or above `main`. Get approval for any gap.
- Refactoring must preserve behavior.

---

## Task Tracking Process

When working through review findings:

1. **Prepare `TODO.md`** - numbered, categorized items with `- [ ]` checkboxes.
2. **Make changes** - implement the selected items.
3. **Validate** - `make all` passes.
4. **Commit** - source changes only, never `TODO.md`.
5. **Mark complete** - check the items off with `- [x]`.
